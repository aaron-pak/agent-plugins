# Upstream

`artifact-diagramming` and `dataviz` are Anthropic's built-in Claude Code skills, captured from Claude Code 2.1.300 (2026-10-15), as are `scripts/markdown-template.html`, `scripts/hljs-runtime.html` and `scripts/hljs-languages.json`. The Artifact tool's text and the `artifact-design` skill are Claude Code's own as well, captured from Claude Code 2.1.301 with `bun run capture`. This note lives outside the skills so that the model reads only Claude Code's text and the plugin's local notes.

- `artifact-diagramming` is verbatim, less one sentence on how an artifact made from an Artifact type draws diagrams.
- `dataviz` is verbatim, with its `references/` and `scripts/` unchanged, in `codex-skills/`, which only Codex's manifest names: Claude Code lists its built-in `dataviz` in every session, so a second copy would only repeat it. It leaves out one sentence of its description on handing chart rows to a first-party document connector.

  `bun run drift` leaves the two sentences out when it compares or refreshes the copies, and says so if Claude Code drops one.
- `artifact-design` is what Claude Code's Skill tool loads for its built-in `artifact-design`, word for word from the page contract on, with Claude Code's listing description as its own. Before the page contract it has one section of the plugin's, "On this machine", which says what doesn't fit a local machine and wins where the two disagree: there are no Artifact types, design systems or runtime capabilities; a `file://` page can't fetch, import or start Workers from its own files; local pages may share one storage origin; outside links need `target="_blank" rel="noopener"`; page files go in the drafts folder; and the skills Claude Code's text names carry the plugin's prefix in Claude Code's Skill tool, which doesn't find a plugin skill by its bare name.
- `artifact-capabilities` keeps the name and listing description of Claude Code's built-in skill, so that the skill listing reads as Claude Code's does. Its body is the plugin's: there are no runtime capabilities here, and it says how a static page does without them.

## The `artifact` server

Claude Code pairs these skills with its Artifact tool and checks pages with `ArtifactCheck`. The plugin's `artifact` MCP server (`mcp/server.mjs`, bundled from `src/`) has a tool of each name.

What it takes from Claude Code:

- **Tool text.** For Claude Code, the Artifact tool's description and input schema are Claude Code's own, word for word (`src/text/native/`), after one paragraph of the plugin's (`src/text/local.md`). That paragraph says claude.ai isn't available here and wins where the text doesn't fit: pages publish to `file://` pages in the artifacts folder, which are their URLs; the claude.ai-only features the text offers (Artifact types, design systems, runtime capabilities, the database and comment tools, the asset store, pinning, watching, sharing) aren't there, so the model makes a plain page without them; a publish sent with an Edit that did not apply goes out without that change, where Claude Code would refuse it; page files go in the drafts folder, since there is no scratchpad; and it gives the tool's full name, the skills' prefixed names and the first-call rule. Claude Code cuts an MCP tool's description at 4,096 characters (2,048 before 2.1.296) and defers MCP tools behind tool search, so the server sends the paragraphs that fit as the tool description, with the local paragraph first so that it survives an older Claude Code's cut, and the rest, in order, as its input schema's description, and asks Claude Code to load the tool up front, as its own Artifact tool is. Claude Code shows an MCP tool's "…" as "...", the one character of the text that reaches the model differently. `quickstart` returns, for every intent, Claude Code's result for a plain page on an account without Artifact types (its lead paragraph and the `artifact-design` skill's text), with the skill's local section after the lead. Claude Code's system prompt also has a paragraph on `edits`, which an MCP server can't add; the description's **To update** paragraph says the same. The server sends no MCP instructions, as Claude Code's tool has none.
- **Parameters.** The server takes every parameter of Claude Code's tool. It acts on the ones that make sense here, including `root` for supporting files, `limit` and `scope: "files"` for `list`, and `path` and `paths` for `read`, and answers the ones only claude.ai can act on in a line: `type_url` and `list`'s types, a non-empty `capabilities`, the asset-store parameters, and `pin` and `unpin`. Those that change nothing here (`label`, `contract`, `force`, `auto_open` and the like) are taken as they are.
- **Publishing.** `publish` wraps the page in the claude.ai skeleton, adds the Mermaid runtime Claude Code adds to a page with diagrams (the same Mermaid 11.16.1 build, loaded from jsDelivr instead of claude.ai) and the highlight.js runtime it inlines in a page with a language-tagged code block (`scripts/hljs-runtime.html`, verbatim), and writes the page to `~/artifacts` (or `ARTIFACTS_DIR`). It unwraps only a skeleton it or claude.ai added, keeping its `lang` and safe-area choice; any other full HTML document goes inside the skeleton as it is. The page's name is the first `<title>` in 8,192 characters, ignoring any after an `<svg>`. Like the Artifact tool's file-to-artifact map, which lasts one session, publishing the same path again updates the same artifact within one session: Claude Code starts a new server for a resumed session but keeps its `CLAUDE_CODE_SESSION_ID`, which each artifact records, and elsewhere the session is the server process. A later session's publish makes a new artifact and names the earlier one.
- **Edits.** `edits` on a publish applies `old_str`/`new_str` pairs by Claude Code's rules (in order, each matching exactly once, all or none, CRLF files edited with LF pairs) and refuses in its words, then saves the edited text to the file unless the file changed during the publish or has other names on disk. The publish result's nudge toward `edits` is Claude Code's, naming its Read and Edit tools; for Codex, which has neither by those names, it and the edit refusals say "read" and "edit" the file.
- **Names and descriptions.** As in Claude Code, a page's `<title>` names its artifact and wins over `title` (the result says when they disagree), a Markdown artifact keeps its file's name, and a page published without a `description` gets one from its meta description, `<h1>` or `<title>`. Where a page has no `<title>`, the plugin writes `title` into it as one, so the local page's tab shows the name.
- **Markdown.** A Markdown file is rendered with marked 16.1.0 (GitHub-flavored, ```` ```mermaid ```` fences as diagrams) into Claude Code's plan template (`scripts/markdown-template.html`, verbatim), with the eyebrow "Markdown · <file>", the file name as the tab title and the opening heading as the page heading, by the same rules as the CLI.
- **ArtifactCheck.** Claude Code 2.1.300 moved preview (and `verify`, which reads what claude.ai viewers' browsers reported) out of the Artifact tool into `ArtifactCheck`, an add-on it doesn't load up front. The server's `ArtifactCheck` has `preview` only. Unlike Claude Code's, it asks Claude Code to load it up front: Claude Code's released build has no local preview, and deferred behind tool search this one went unused on dashboards, where the skill says to take the look (0 of 4 runs, against 3 of 3 loaded up front). Codex loads it with the rest of the server. Its description is Claude Code's for a local preview, less the sentence on runtime capabilities, and its action's description is Claude Code's for `preview`, plus the two checks below; it takes `widths` and `themes` as Claude Code's does and refuses values outside Claude Code's schema. `preview` renders a page with `ArtifactCheck`'s widths, themes, step timeouts, checks and report (less what the report says claude.ai's published viewer does), and returns captures sized as `ArtifactCheck` sizes them. Claude Code's preview loads only the page, its Mermaid runtime and Google Fonts and reports CDN scripts as blocked; this one also loads scripts from the five CDNs the page contract allows, as the page published here does, and reports one that the network doesn't deliver within 8 seconds or that answers with an HTTP error. The page's own files are listed in a note, and it declines a Markdown file in `ArtifactCheck`'s words. In the public 2.1.300 build, Claude Code's local preview is compiled out, so there the check-once paragraph comes down to a screenshot or no look.

Where a local machine can't do what claude.ai does, it differs:

- **The link** is a `file://` page on this machine, so the publish result says to share the published `index.html`, or its folder without `.versions` for a page with other files (not the source file), in place of claude.ai's private-sharing and live-subscription paragraphs, and says when the page was not opened.
- **The page** carries a Content-Security-Policy meta that mirrors the viewer: Claude Code's own model of it (its preview's policy) plus the five script CDNs the page contract allows, without that policy's `webrtc 'block'`, which Chromium logs as an error on every load. The Mermaid runtime is skipped for a page that loads Mermaid itself with a `<script src>`. A file that was a full HTML document gets a note asking for page content only next time, and `read` returns the page without its skeleton and says publishing adds it.
- **Edit, then publish.** Claude Code refuses an Artifact publish sent in the same response as an Edit that did not apply. Nothing tells an MCP server that, so the local paragraph says the publish goes out without that change.
- **Inputs.** Paths must be absolute, because Codex starts the server in the plugin's folder. Links are accepted percent-encoded or not, as a folder or as its `index.html`. A parameter Claude Code's tool doesn't have is refused by name, and supporting files are all checked before anything is written.
- **The artifacts folder.** Publishing a page from inside it updates that artifact, a new artifact never takes a folder that is already on disk, and an unreadable `index.json` is set aside and rebuilt from the artifact folders.
- **Drafts.** Claude Code lists a scratchpad only for some accounts (behind a flag, or with its own Artifact tool on), so the local paragraph and the skill's local section send page files to a private drafts folder per session in the system temp directory. Writes there get the usual permission check, which auto mode's reviewer passes; unlike the scratchpad, the other modes ask.
- **Preview.** `ArtifactCheck` is listed only when a startup check finds Playwright and a Chromium, and `ARTIFACT_PREVIEW=0` turns it off. The tool's listing takes the previous start's answer, kept in the temp folder, so that it doesn't wait for the check: Claude Code doesn't wait long for a plugin's server before the first turn, and a server still starting leaves the model without the tool. It finds Playwright beside the script or installed globally, never in the project (the startup check would otherwise run the project's code), launches Playwright's full Chromium or an installed browser from Claude Code's own list when Playwright's headless browser is missing, and resizes captures in that browser instead of with `sharp`. It also runs two checks `ArtifactCheck` lacks, for layout bugs that test pages from both tools shipped: running text that a grid or flex parent splits into separate rows or columns, and an SVG whose labels draw too small to read at phone width (under 7.5 px).
- **Codex.** Codex drops every description from an input schema over 5,000 bytes (and cuts a tool description at 1,000 bytes for an Agent Plugins manifest, which this plugin no longer uses), so Claude Code's text can't reach a Codex model whole. When the client is Codex the server sends a compact tool of its own, with the lead, the first-call rule, the calls and the page contract's essentials, and leaves the rest to `quickstart`, which is the same as for Claude Code. That compact text names nothing the plugin lacks. Codex passes a plugin's server only a fixed list of variables, so the manifest's `env_vars` names the server's own, Playwright's and the desktop ones a browser needs to open on Linux.
