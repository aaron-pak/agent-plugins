# Upstream

The three skills are Anthropic's built-in Claude Code skills, captured from Claude Code 2.1.310 (2026-10-23), as are `scripts/markdown-template.html`, `scripts/hljs-runtime.html` and `scripts/hljs-languages.json`. This note lives outside the skills so that the model reads only Claude Code's text.

- `artifact-diagramming` is verbatim, less one sentence on how an artifact made from an Artifact type draws diagrams.
- `dataviz` is verbatim, with its `references/` and `scripts/` unchanged, in `codex-skills/`, which only Codex's manifest names: Claude Code lists its built-in `dataviz` in every session, so a second copy would only repeat it. It leaves out one sentence of its description on handing chart rows to a first-party document connector.

  Artifact types and that connector exist only on claude.ai, and the skills here name nothing the plugin doesn't have. `bun run drift` leaves the two sentences out when it compares or refreshes the copies, and says so if Claude Code drops one.
- `artifact-design` keeps Claude Code's wording. The page contract and guidance are also what the Artifact tool's `quickstart` returns for a plain page, and the `artifact` server reads them from this `SKILL.md`. The only edits:
  1. Frontmatter: `description` and `when_to_use` are merged into one description, with example page types, so the skill loads without a tool forcing it.
  2. A "The tools here" section is added. It names the server's `Artifact` tool with its full names in Claude Code and Codex and its `ArtifactCheck` tool, lists the Artifact tool's actions and publish parameters, and maps Claude to this harness. `quickstart` leaves it out, since its text starts at the page contract. For the same reason, "CLAUDE.md" in Respect what already exists reads "CLAUDE.md or AGENTS.md".
  3. Removed, because only claude.ai can do them: the pointers to runtime capabilities and the `db` store, the Artifact-type note, and Open viewers. The device-API sentence in the page contract takes the shape of the variant Claude Code uses where a page can't be granted runtime capabilities, with "ask the viewer and are often refused or missing" for "are refused without a prompt", since a browser asks before it opens a camera for a local page.
  4. The check-once paragraph offers one `ArtifactCheck` preview, without Claude Code's fallback to the Artifact tool's own `preview` action, which this plugin's Artifact tool doesn't have. Where `ArtifactCheck` isn't listed, `quickstart` leaves it out of that sentence. "Review happens on the live page" reads "on the published page".
  5. The page contract's sentences on Web Workers, fetching the page's own files, canvas export and storage origin describe a page opened from a `file://` link, which is how an artifact published here opens: such a page cannot fetch its own files or start Workers from them, and may share one storage origin with every other local page.
  6. Sentences about claude.ai's viewer and gallery are reworded for a page opened from this machine, keeping each rule a page follows. The title and description no longer mention the gallery and its cards: the title names the page in the browser tab and in `list`, and the description goes in the page's meta description. Thumbnails, shared-link previews and republishes that keep form state are no longer mentioned. The body's background is explained by the browser's default ground instead of the viewer's. The frame paragraph is now "What the page can do" and drops the viewer audiences, organizations and app views. A `window.open` outside a click is blocked as a pop-up, and the claude:viewport-fit-sides meta, which only claude.ai's apps read, is left out. The band painted above a sticky header keeps content from scrolling under the phone's status bar rather than the host's controls. `alert()`, `confirm()` and `prompt()` are ruled out as a rule rather than as the viewer's behavior. The sentence that ruled out download links goes, because a page opened from this machine can download. The viewer's other limits, which a page opened from this machine doesn't have, become the rules a page follows: no Print button or `window.print()`; email, phone and app links depend on the viewer's device; outside links carry `target="_blank" rel="noopener"`, since on a local page they would replace it; don't build on reading the clipboard; device APIs ask and are often refused; service workers don't work and WebRTC stays out; deep links use a plain `#anchor` and keep other state in the page, and the page doesn't change its own URL otherwise; the tokens the viewer keeps for itself, and the address bar that doesn't follow the page, go. The theme's three states come from a toggle on the page or a preview's theme instead of the viewer's setting, and a single-theme page looks right in either browser theme instead of on either host background.

  Two things Claude Code fills in when it builds the skill text are written out as it fills them today: the script-hosts sentence, which it composes from its CDN list, and the dataviz callout, which it adds only behind a feature flag that is off (the `<!-- dataviz-callout -->` marker is dropped, and `quickstart` keeps the blank lines it leaves). If the flag turns on, Claude Code's text gains a pointer to `dataviz` that this copy lacks; `bun run drift` doesn't watch flags.

## The `artifact` server

Claude Code pairs these skills with its Artifact tool and checks pages with `ArtifactCheck`. The plugin's `artifact` MCP server (`mcp/server.mjs`, bundled from `src/`) has a tool of each name. Its text names no tool, type or service the plugin lacks: where Claude Code's says what only claude.ai does, it is left out, and a test checks the tool listings for those names.

What it takes from Claude Code:

- **Tool text.** The tool description is adapted from the Artifact tool's, including the rule that a new artifact starts with a `quickstart` call and its full name, and the `quickstart` result matches Claude Code's for an account without Artifact types for intent `other`, plus one line asking for the `artifact-diagramming` skill when the page includes a diagram, and less Claude Code's lines on listing Artifact types and Design Systems. Claude Code's agents loaded that skill for a diagram on their own in every run of a 2.1.300 comparison, and the plugin's agents, which take the guidance from `quickstart` instead of a skill, in none. `quickstart` takes no `intent` or `design_systems`, since every artifact here is a plain page, and ignores either one passed anyway. With an `intent` to pick, the plugin's agents called explainers a `document` where Claude Code's picked `other`, and in a blind comparison against a build that copied Claude Code's text word for word with a local note on top, judges preferred the pages made with this text and no `intent` in 38 of 48 votes. The description's Artifact types paragraph becomes New artifacts, which keeps its first-call rule without the `intent`. Its opening says finished work isn't done while it sits in terminal scrollback "or in a file it hasn't published", for Claude Code's "or in a local file", since a published page is a local file here. Claude Code cuts an MCP tool's description at 4,096 characters (2,048 before 2.1.296) and defers MCP tools behind tool search, so the server sends the paragraphs that fit as the tool description, with the first-call rule after the first one so that it survives an older Claude Code's cut, and the rest, in order, as its input schema's description, and asks Claude Code to load the tool up front, as its own Artifact tool is. The description also leaves out claude.ai's examples of pages people use (collecting input, tracking changes, live data, all runtime capabilities) and "so the post can carry the link", since a local link can't be posted; its exception for misleading or sensitive content lets the person decide whether to publish rather than whether the page gets a URL. Where it says to load a skill, it gives the name Claude Code's Skill tool takes for a plugin's skill (`artifact-design:artifact-design`, and for the diagram line, `artifact-design:artifact-diagramming`). `quickstart` adds "In this text, Claude means you", since its text starts after the skill's tools section. The server's MCP instructions are one line on the first call; Claude Code's tool has none.
- **Publishing.** `publish` wraps the page in the claude.ai skeleton, adds the Mermaid runtime Claude Code adds to a page with diagrams (the same Mermaid 11.16.1 build, loaded from jsDelivr instead of claude.ai) and the highlight.js runtime it inlines in a page with a language-tagged code block (`scripts/hljs-runtime.html`, verbatim), and writes the page to `~/artifacts` (or `ARTIFACTS_DIR`). It unwraps only a skeleton it or claude.ai added, keeping its `lang` and safe-area choice; any other full HTML document goes inside the skeleton as it is. The page's name is the first `<title>` in 8,192 characters, ignoring any after an `<svg>`. Like the Artifact tool's file-to-artifact map, which lasts one session, publishing the same path again updates the same artifact within that session, resumed or not (see The artifacts folder); another session's publish makes a new artifact and names the earlier one.
- **Edits.** `edits` on a publish applies `old_str`/`new_str` pairs by Claude Code's rules (in order, each matching exactly once, all or none, CRLF files edited with LF pairs) and refuses in its words, then saves the edited text to the file unless the file changed during the publish or has other names on disk. Claude Code also teaches `edits` in a system-prompt section; the plugin can't add one, so the tool description's **To update** paragraph, which says the same, carries it. The publish result's nudge toward `edits`, and the edit refusals, say "read" and "edit" the file rather than naming Claude Code's Read and Edit tools, which Codex doesn't have.
- **Names and descriptions.** As in Claude Code, a page's `<title>` names its artifact and wins over `title` (the result says when they disagree), a Markdown artifact keeps its file's name, and a page published without a `description` gets one from its meta description, `<h1>` or `<title>`. Where a page has no `<title>`, the plugin writes `title` into it as one, so the local page's tab shows the name.
- **Markdown.** A Markdown file is rendered with marked 16.1.0 (GitHub-flavored, ```` ```mermaid ```` fences as diagrams) into Claude Code's plan template (`scripts/markdown-template.html`, verbatim), with the eyebrow "Markdown · <file>", the file name as the tab title and the opening heading as the page heading, by the same rules as the CLI.
- **ArtifactCheck.** Claude Code 2.1.300 moved preview (and `verify`, which reads what claude.ai viewers' browsers reported) out of the Artifact tool into `ArtifactCheck`, an add-on it doesn't load up front. The server's `ArtifactCheck` has `preview` only. Unlike Claude Code's, it asks Claude Code to load it up front: Claude Code's released build has no local preview, and deferred behind tool search this one went unused on dashboards, where the skill says to take the look (0 of 4 runs, against 3 of 3 loaded up front). Codex loads it with the rest of the server. Its description is Claude Code's for a local preview, less the sentence on runtime capabilities, and its action's description is Claude Code's for `preview`, plus the two checks below; it takes `widths` and `themes` as Claude Code's does and refuses values outside Claude Code's schema. `preview` renders a page with `ArtifactCheck`'s widths, themes, step timeouts, checks and report (less what the report says claude.ai's published viewer does), and returns captures sized as `ArtifactCheck` sizes them. Claude Code's preview loads only the page, its Mermaid runtime and Google Fonts and reports CDN scripts as blocked; this one also loads scripts from the five CDNs the page contract allows, as the page published here does, and reports one that the network doesn't deliver within 8 seconds or that answers with an HTTP error. The page's own files are listed in a note, and it declines a Markdown file in `ArtifactCheck`'s words. In the public 2.1.300 build, Claude Code's local preview is compiled out, so there the check-once paragraph comes down to a screenshot or no look.

Where a local machine can't do what claude.ai does, it differs:

- **The link** is a `file://` page on this machine, so the publish result says to share the published `index.html`, or its folder without `.versions` for a page with other files (not the source file), and says when the page was not opened. Because of that link, the description's supporting-files paragraph and the skill's page contract say what such a page can't do with its own files (`fetch()`, module scripts, Workers, canvas export) and that local pages may share one storage origin.
- **The page** carries a Content-Security-Policy meta that mirrors the viewer: Claude Code's own model of it (its preview's policy) plus the five script CDNs the page contract allows, without that policy's `webrtc 'block'`, which Chromium logs as an error on every load. The Mermaid runtime is skipped for a page that loads Mermaid itself with a `<script src>`. A file that was a full HTML document gets a note asking for page content only next time, and `read` returns the page without its skeleton and says publishing adds it.
- **Edit, then publish.** Claude Code refuses an Artifact publish sent in the same response as an Edit that did not apply. Nothing tells an MCP server that, so the description says the publish goes out without that change.
- **Inputs.** Paths must be absolute, because Codex starts the server in the plugin's folder. Links are accepted percent-encoded or not, as a folder or as its `index.html`. An unknown parameter is refused by name (for `type_url`, `capabilities` and the asset-store ones, with what to do here instead), and supporting files are all checked before anything is written.
- **The artifacts folder.** Publishing a page from inside it updates that artifact, a new artifact never takes a folder that is already on disk, and an unreadable `index.json` is set aside and rebuilt from the artifact folders. A session outlives its server: a resumed one starts a new server, and Claude Code switches sessions under a running one (an in-app resume, `/clear`) without telling it. So each artifact lists the last eight Claude Code sessions that published it, from the `CLAUDE_CODE_SESSION_ID` Claude Code gives a server when it starts it, and a file in a drafts folder, which only the conversation that wrote it knows, counts as that conversation's; that also covers Codex, which passes no session ID. Some cases still differ from Claude Code's. A running server keeps the session ID it started with, so after `/clear`, which empties Claude Code's map, republishing a path from before it updates that artifact, and after an in-app resume, a file outside the drafts that the resumed session published under its own ID makes a new artifact, naming the old one, while what it publishes is filed under the server's ID. A session forked with `--fork-session` updates its parent's artifact when it republishes a file in the drafts, and makes a new one, naming the parent's, for a file elsewhere. A path another session published since makes no difference: each publish finds the newest artifact of that path that its own session published.
- **Drafts.** Claude Code lists a scratchpad only for some accounts (behind a flag, or with its own Artifact tool on), so the description and the `quickstart` result send page files to a private drafts folder per session in the system temp directory. Claude Code's own tool names no folder when there is no scratchpad. Writes there get the usual permission check, which auto mode's reviewer passes; unlike the scratchpad, the other modes ask.
- **Preview.** `ArtifactCheck` is listed only when a startup check finds Playwright and a Chromium, and `ARTIFACT_PREVIEW=0` turns it off. The tool's listing takes the previous start's answer, kept in the temp folder, so that it doesn't wait for the check: Claude Code doesn't wait long for a plugin's server before the first turn, and a server still starting leaves the model without the tool. It finds Playwright beside the script or installed globally, never in the project (the startup check would otherwise run the project's code), launches Playwright's full Chromium or an installed browser from Claude Code's own list when Playwright's headless browser is missing, and resizes captures in that browser instead of with `sharp`. It also runs two checks `ArtifactCheck` lacks, for layout bugs that test pages from both tools shipped: running text that a grid or flex parent splits into separate rows or columns, and an SVG whose labels draw too small to read at phone width (under 7.5 px).
- **Codex.** Codex drops every description from an input schema over 5,000 bytes (and cuts a tool description at 1,000 bytes for an Agent Plugins manifest, which this plugin no longer uses), so when the client is Codex the server sends a compact tool with the lead, the first-call rule, the calls and the page contract's essentials, and leaves the rest to `quickstart`. Codex passes a plugin's server only a fixed list of variables, so the manifest's `env_vars` names the server's own, Playwright's and the desktop ones a browser needs to open on Linux.
